### 1. SUMMARY AND OVERALL IMPACT STATEMENT

This manuscript presents version 2.0/2.15 of `[SOFTWARE]`, an open-source pipeline for processing Duplex Sequencing (DS) data to call Single-Strand Consensus Sequences (SSCS) and Duplex Consensus Sequences (DCS). The update introduces three engineering modifications: (1) reference-free duplex barcode error correction (`baralign.sh` and `correct.py`), which indexes all concatenated $12+12 = 24\text{-bp}$ duplex tags using `Bowtie` (FM-index), aligns all tags against the index within edit distance $d \in \{1, 2, 3\}$, constructs undirected connected-component graphs in `networkx`, and assigns all reads in each component to the barcode with the highest read count; (2) replacement of the `MAFFT` multiple sequence aligner with `Kalign2` called directly from Python via C bindings; and (3) a buffered worker queue ($M \times W$ with $M=8$) in `align-families.py` to mitigate synchronization bottlenecks in Python's `multiprocessing` module. The authors evaluate the pipeline on simulated duplex datasets (400,000 and 40,000 read pairs) and two empirical datasets (`ABL1` and plasmid `pBR322`). Source code (`GitHub`), `Bioconda` packages, and `[WORKFLOW_PLATFORM]` workflows are publicly available.

The algorithmic engineering—using an FM-index to avoid $O(n^2)$ pairwise barcode comparisons without requiring reference-genome alignment, and integrating `Kalign2` with buffered multiprocessing to achieve an $\sim 6\text{--}9\times$ wall-clock speedup (Table 3)—is practical and well-motivated. However, the manuscript suffers from three severe internal inconsistencies in its empirical and simulation tables that require resolution before the accuracy and yield claims can be trusted: (1) in Table 1 (`pBR322`), as the barcode mismatch threshold increases from $0$ to $3$, `SSCS ab` and `SSCS ba` counts *decrease* monotonically by $>10,500$ (to $73,647$ and $73,160$), whereas `DCS` counts increase to $89,513$—an impossibility under standard definitions because every DCS requires pairing one `SSCS ab` and one `SSCS ba` ($\text{DCS} \le \min(\text{SSCS}_{ab}, \text{SSCS}_{ba})$), while the main text (Line 38) falsely states that error correction increased overall SSCS; (2) in Table 4 (Line 80), the reported per-base consensus error rate of simulated Duplex Sequencing is $0.525\%\text{--}0.563\%$ ($5.3 \times 10^{-3}$ errors/base), which is five times *higher* than the simulated raw sequencing error rate ($0.1\%$, Line 110) and five orders of magnitude worse than authentic Duplex Sequencing ($\sim 10^{-7}\text{--}10^{-9}$); and (3) in Table 2, sensitivity/recall ($67.28\%$ and $77.97\%$ of erroneous barcodes corrected) is misclassified as the "True Negative" rate. These issues point to unexamined simulation/counting bugs and mislabeled table columns that can and must be corrected via code auditing and re-tabulation.

### 2. SPECIFIC CONCLUSIONS AND ASSESSMENT OF SUPPORT

* **Replacing `MAFFT` with in-memory `Kalign2` C bindings and buffered multiprocessing reduces family alignment wall-clock runtime by $6\text{--}9\times$: [Well Supported].**  
  Figure 4 and Table 3 provide clear, controlled timing and memory comparisons across 1 to 32 CPUs, isolating the contributions of `Kalign2` ($\sim 6\text{--}8\times$ faster at typical family sizes of $\sim 12$ reads) and the $M \times W$ job queue ($\sim 2\times$ speedup at 16–32 CPUs). The authors also transparently report a 3-trial control showing that when queue size equals worker count ($32$), version 2.15 has a $27\%$ higher overhead than version 0.4.

* **FM-index (`Bowtie`) all-vs-all barcode alignment with connected-component graph merging increases empirical SSCS and DCS yield (Table 1): [Methodologically Flawed].**  
  In Line 38, the authors claim that barcode error correction succeeds in *"increasing the overall SSCS and DCS."* Yet Table 1 shows the exact opposite for SSCS: as allowed mismatches increase from $0 \to 1 \to 2 \to 3$, `SSCS ab` drops from $38,493 \to 36,280$ in `ABL1` and from $84,231 \to 73,647$ in `pBR322` (with identical drops in `SSCS ba`). Even more troublingly, in `pBR322` at edit distances 2 and 3, the reported number of Duplex Consensus Sequences (`DSC` $= 84,359$ and $89,513$) is strictly greater than the number of single-strand consensus sequences (`SSCS ab` $= 78,481$ and $73,647$; `SSCS ba` $= 78,234$ and $73,160$). Because each DCS is formed by pairing complementary `ab` and `ba` SSCSs (Figure 1, Line 12), $\text{DCS}$ cannot exceed $\text{SSCS}_{ab}$ or $\text{SSCS}_{ba}$ unless Table 1 is reporting *unpaired residual* SSCSs without stating so, or single-linkage graph chaining is erroneously collapsing distinct SSCS families while double-counting DCS pairs.

* **Simulated Duplex Sequencing consensus accuracy improves from $0.563\%$ (`MAFFT`) to $0.525\%$ (`Kalign2` + error correction) vs. $1.140\%$ (`Loeb` pipeline) errors per base (Table 4): [Methodologically Flawed].**  
  As stated in the Background (Line 12), Duplex Sequencing is designed to detect variants at frequencies of $10^{-5}\text{--}10^{-9}$ where conventional sequencing fails below $1\%$. Yet in Table 4 and Line 80, `[SOFTWARE]` yields $0.00525\text{--}0.00563$ errors per output base ($0.525\%\text{--}0.563\%$), and the standard Loeb pipeline yields $0.0114$ errors per base ($1.14\%$). A consensus error rate of $0.5\%\text{--}1.1\%$ is **worse than a single raw uncorrected read** simulated at an error rate of $0.001$ ($0.1\%$, Line 110). Looking at the simulator description in Methods (Line 110: *"For a family size of n, the process starts with n reads at the root node representing the original fragment molecule... Once a tree is generated, errors are simulated at each node and propagated to their descendents"*), either root-level/first-cycle errors are being shared across both strands in the simulator, or consensus base calls are being compared to the reference without coordinate alignment (so that a 1-bp indel or linker-trimming shift causes every downstream base in the read to be scored as a mismatch).

* **Barcode error correction achieves $>99.7\%$ precision and $67.28\%\text{--}77.97\%$ sensitivity on simulated barcodes (Table 2): [Fragile].**  
  While the underlying counts cited in the prose (Line 48: 5 false corrections out of 816,335 at $d=1$; 2,740 out of 936,582 at $d=3$) indicate low false-merge rates in a 400,000-read simulation, Table 2's confusion matrix is misconstructed: the recall of erroneous barcodes ($\text{TP}/(\text{TP}+\text{FN}) = 67.281\%$) is labeled as `True Negative (%)`, and its complement ($32.721\%$) is labeled as `False Negative (%)`, directly contradicting the table footnote. Furthermore, simulating only 400,000 reads ($\sim 43,344$ families) leaves the 24-mer barcode space ($4^{24} \approx 2.8 \times 10^{14}$) vastly sparser than high-depth empirical libraries ($10^7\text{--}10^9$ molecules), and `correct.py` uses single-linkage connected components (`networkx`) with a 2-bp alignment start offset (`--distance 2`, Line 108), which is vulnerable to "snowball" chaining at $d=3$ in dense barcode spaces or when oligonucleotide synthesis has non-uniform base composition.

### 3. CONSTRUCTIVE AND DOABLE SUGGESTIONS FOR IMPROVEMENT

#### 1. Resolve the Mathematical Contradiction Between `SSCS` and `DCS` Counts in Table 1
* **WHY:** A Duplex Consensus Sequence (DCS) is constructed by pairing an `ab` SSCS with its complementary `ba` SSCS, meaning total DCS count can never exceed $\min(\text{total SSCS}_{ab}, \text{total SSCS}_{ba})$. In Table 1 (`pBR322`), `DCS` rises to $89,513$ while `SSCS ab` drops to $73,647$, contradicting both the definition of DCS and the text on Line 38 claiming that SSCS counts increased.
* **WHAT:** Audit the script that generated Table 1 to determine whether `SSCS ab` and `SSCS ba` in Table 1 represent *only unpaired* SSCSs remaining after DCS formation (in which case total $\text{SSCS}_{ab} = \text{unpaired SSCS}_{ab} + \text{DCS}$, which rises from $84,231 + 77,164 = 161,395$ at $d=0$ to $73,647 + 89,513 = 163,160$ at $d=3$) or whether families are being over-merged.
* **HOW:** Report both **Total SSCS** ($\text{paired} + \text{unpaired}$) and **Paired DCS** in Table 1, verify that $\text{DCS} \le \min(\text{Total SSCS}_{ab}, \text{Total SSCS}_{ba})$ for every row, and update Line 38 to accurately describe why unpaired SSCSs decrease as more single-strand families are successfully paired into DCSs.

#### 2. Audit and Fix the Simulator / Evaluator Producing a $0.56\%$ Consensus Error Rate in Table 4
* **WHY:** Duplex Sequencing consensus error rates should be $\le 10^{-7}$ errors/base when raw PCR/sequencing error rates are $10^{-3}$ (since requiring $\ge 3$ reads per strand with $\ge 0.7$ consensus threshold and matching both strands independently suppresses independent errors to $\sim (10^{-3})^2$ or lower). Reporting $0.525\%\text{--}1.140\%$ errors/base in Table 4 implies a bug in either the simulator's strand tree generation or the error-counting alignment script.
* **WHAT:** Check whether (a) the simulator in Line 110 introduces mutations at the root node *prior* to splitting the forward (`ab`) and reverse (`ba`) template strands (which would create fake somatic mutations present on both strands, rather than PCR/sequencing errors), or (b) the evaluation script compares DCS output strings to the true fragment by positional index without accounting for 5' `trimmer.py` clipping or 1-bp indels.
* **HOW:** Fix the simulator so the two original template strands diverge at the root *before* PCR replication errors occur, align DCS outputs to the true reference fragments before counting base substitutions, and recompute Table 4.

#### 3. Reconstruct Table 2 Using Standard Confusion Matrix Definitions and Guard Against Single-Linkage Chaining
* **WHY:** In Table 2, the columns `Positive (%)` and `Negative (%)` sum to $100\%$ vertically, placing the sensitivity of error correction ($67.281\%$) in the `True Negative` cell and omitting true negatives (barcodes without errors that were correctly left untouched). Additionally, single-linkage connected components in `correct.py` can chain distant barcodes at edit distance $d=3$.
* **WHAT:** Reformat Table 2 to clearly report: (1) Total error-free barcodes (True Negatives = untouched, False Positives = erroneously altered), (2) Total error-containing barcodes (True Positives = corrected to true parent barcode, Mis-corrected = altered to wrong barcode, False Negatives = left uncorrected), Precision, and Recall/Sensitivity. In `correct.py`, constrain barcode merging by requiring star-like topology (distance $\le d$ directly to the centroid/hub barcode rather than arbitrary path length in a connected component).
* **HOW:** Re-tabulate the 400,000-read simulation log into standard contingency counts and percentages in Table 2, and add a direct centroid-distance check in `correct.py`.
